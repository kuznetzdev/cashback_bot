# Product Overview

## 0. Короткое описание

Проект — это кроссплатформенное веб-приложение для управления банковским кэшбэком, которое помогает пользователю собирать данные по картам из разных банков, проверять и редактировать их, а затем получать понятные рекомендации, какой картой платить в конкретной категории, чтобы максимизировать выгоду.

## 0.1. Бизнесовое описание

Проект направлен на создание user-centric fintech utility product, который сокращает потери выгоды из-за фрагментации банковских предложений, упрощает работу с ежемесячно меняющимися категориями кэшбэка и превращает сложные условия банков в простой, быстрый и полезный пользовательский опыт на мобильных и десктопных устройствах.

## 1. Общая бизнес-цель

Продукт нужен для повседневного управления выгодой от банковского кэшбэка.

Главная задача системы:

- не просто хранить категории
- а помогать пользователю быстро принимать решение, какой картой платить в конкретной ситуации, чтобы получать максимальную выгоду

Ключевая идея:

у пользователя есть несколько банковских карт с разными категориями, условиями и сроками. В реальной жизни он не держит это в голове постоянно, из-за чего платит не той картой и теряет деньги.

## 2. Что это за продукт

Это единое приложение для:

- загрузки данных о кэшбэке
- OCR-распознавания скриншотов
- ручного ввода и редактирования
- хранения предложений по банкам и картам
- сравнения предложений между собой
- выбора лучшей карты под конкретную категорию

Продуктовый фокус:

- управление будущей выгодой
- decision support в момент покупки

Продукт не является:

- финансовой бухгалтерией
- учетом расходов
- учетом реально начисленного кэшбэка
- менеджером транзакций

## 3. Какую проблему решает продукт

### Разрозненность информации

Данные лежат в разных банковских приложениях. Чтобы понять, чем платить за АЗС, такси или рестораны, пользователь вынужден открывать несколько приложений и помнить их логику.

### Сложность сравнения

Даже если категории известны, пользователь обычно не помнит:

- процент
- лимит
- срок действия
- дополнительные условия
- исключения

### Потеря выгоды в моменте

Решение о выборе карты принимается быстро, прямо на кассе. Если ответ нельзя получить за 2-3 действия, продукт не решает основную задачу.

### Высокая стоимость сопровождения

Кэшбэк меняется часто, нередко ежемесячно. Пользователь быстро бросает заметки и таблицы, если продукт не делает обновление простым.

### Потеря доверия без ручного подтверждения

OCR и ручной ввод неизбежно дают ошибки. Если пользователь не может проверить и исправить результат, доверие к системе падает.

## 4. Предлагаемое решение

Продукт строится как личный менеджер кэшбэка:

- собирает данные из разных банков в одном месте
- нормализует категории
- позволяет проверить и поправить результат
- показывает не сырые данные, а практическую рекомендацию

Пример желаемой ценности:

не просто "по карте X есть 5% на рестораны", а:

"Для ресторанов сейчас выгоднее платить картой X. Резервный вариант: карта Y."

Дальнейший уровень продукта:

- учитывать лимиты
- учитывать срок действия
- учитывать свежесть данных
- учитывать пользовательские исключения

## 5. Ценность для пользователя

### Базовая

- экономия денег
- экономия времени
- снижение когнитивной нагрузки
- единое место хранения информации

### Практическая

Продукт должен быстро отвечать на вопросы:

- чем платить в супермаркете
- чем платить за такси
- чем платить на маркетплейсе
- какая карта лучшая для АЗС
- какие данные уже устарели
- что пора обновить

## 6. Целевая аудитория

### Основной сегмент

Пользователи с 2+ картами, которые:

- уже интересуются кэшбэком
- готовы один раз настроить систему
- хотят максимизировать выгоду без постоянной ручной рутины

### Подсегменты

- финансово дисциплинированные пользователи
- охотники за выгодой
- занятые пользователи
- digital-first аудитория

## 7. Почему web-приложение

Web дает лучший баланс между:

- скоростью запуска
- доступностью на любом устройстве
- единым кодовым контуром
- быстрыми продуктовыми итерациями

### Почему важен mobile web

Основной повседневный сценарий происходит со смартфона:

- быстро загрузить скриншот
- быстро найти нужную категорию
- быстро понять, чем платить прямо сейчас

### Почему важен desktop web

Desktop нужен для более "управленческого" режима:

- настройка
- массовое редактирование
- сравнение нескольких карт
- обзор аналитики
- работа с историей

## 8. UX-принципы продукта

### Не финансовый кабинет, а рабочий инструмент

Интерфейс должен быть построен вокруг задач:

- "чем платить"
- "обновить данные"
- "проверить, что выгоднее"

А не вокруг перегруженного списка сущностей.

### Быстрый first value

Пользователь должен быстро увидеть пользу:

- загрузил
- проверил
- сохранил
- увидел лучшую карту

### Минимум трения

- не перегружать длинными формами
- не заставлять помнить скрытые правила
- не создавать тупиковых экранов

### Доверие к данным

Пользователь должен понимать:

- откуда данные
- насколько они свежие
- были ли они подтверждены вручную

### Editing-first

Редактирование должно быть встроено в продукт как норма, а не как дополнительная редкая функция.

## 10. Бизнес-модель

Потенциальные варианты:

### Freemium

- бесплатно: ограниченное число карт, базовый рейтинг, базовый ввод
- платно: больше карт, аналитика, напоминания, расширенная история, рекомендации

### Подписка

Пользователь платит за:

- удобство
- автоматизацию
- экономию времени
- более качественные рекомендации

### Партнерская модель

Возможные будущие направления:

- рекомендации финансовых продуктов
- white-label для финтеха
- B2B-интеграции

На раннем этапе это не основной фокус.

## 11. Текущий baseline и целевое развитие

### Уже реализовано в текущем baseline

- core-first архитектура
- Telegram adapter
- web adapter
- PostgreSQL storage
- OCR screenshot parsing
- manual input
- template input
- preview/edit/save flow
- редактирование сохраненного банка
- ranking по категориям
- глобальный рейтинг
- text intents для поиска и удаления
- settings
- reminders
- action history в `user_logs`
- interruption/recovery flow

### Что является следующим этапом развития, но не текущим baseline

- отдельная сущность карты с типом карты
- лимиты по категории
- сроки действия категории
- специальные условия и комментарии
- признак подтвержденности данных на уровне item
- полноформатная история по месяцам
- устаревание данных по policy
- desktop-режим с массовым редактированием
- более сложная decision logic с лимитами и сроками
- тарифы, freemium, billing
- семейный режим

## 12. Продуктовые ограничения

Чтобы не размыть продукт, нужно сохранять фокус.

Продукт не должен превращаться в:

- учет личных финансов
- банковский агрегатор транзакций
- приложение для ведения бюджета
- систему учета начисленных cashback-платежей

Его ядро:

- актуальные предложения банков
- их нормализация
- выбор лучшей карты под сценарий покупки

## 13. Критерии хорошего продукта

Продукт можно считать удачным, если пользователь:

- быстро добавляет свои данные
- доверяет результату после preview
- за секунды понимает, чем платить
- не теряет данные при прерывании сценария
- регулярно возвращается обновлять категории
- ощущает, что система помогает принимать более выгодные решения
